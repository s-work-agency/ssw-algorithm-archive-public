# 샘플 안내

이 사이트는 아카이브 본체가 아니라 **밖에서 볼 수 있게 잘라 낸 공개 스냅샷**입니다. 무엇이
담겨 있고, 화면에서 어떤 순서로 보면 되는지를 정리했습니다.

> **공개 사이트 주소**: https://s-work-agency.github.io/ssw-algorithm-archive-public/
> 이 저장소가 그대로 서빙됩니다.

---

## 1. 스냅샷이라는 뜻

- **2026년 8월 시점**의 내용을 한 번 잘라 온 것입니다.
- **본체가 갱신돼도 따라가지 않습니다.** 자동 동기화가 없는 일회성 사본입니다.
- 본체 구현과 콘텐츠는 비공개 저장소에 있습니다. 여기에는 공개하기로 한 8종만 실려 있습니다.

정적 사이트라 서버가 없습니다. 산출물은 HTML · CSS · JS와 데이터 파일 한 벌이고, 화면에
보이는 모든 값은 그 데이터에서 나옵니다. 조회 API를 따로 두지 않았기 때문에 상세 · 소스 본문 ·
공식 벡터까지 전부 정적 파일로 함께 실려 있습니다.

대신 **받은 바이트를 화면이 직접 검사합니다.** 파일을 하나 받을 때마다 인덱스와 상세가
발표한 `sha256` · `byteLength`와 정확히 일치하는지 보고, 어긋나면 코드 표시도 복사도 테스트
렌더도 하지 않습니다. Content-Type 같은 헤더는 검사에 넣지 않았습니다. 정적 서버마다 표기가
갈리고, **헤더는 서버가 말하는 것이지만 해시는 바이트가 말하는 것**이기 때문입니다.

## 2. 담긴 것: 8종 × 3개 언어 = 24개 구현

| 알고리즘 | 분류 | 무엇을 보여 주는가 |
|---|---|---|
| 퀵 정렬 | 정렬 | 비교 기반 정렬. 분할 기준과 동률 처리가 계약에서 어떻게 잠기는지 |
| 버블 정렬 | 정렬 | 가장 단순한 비교 정렬. 같은 결과에 이르는 길이 하나가 아니라는 대조 |
| 계수 정렬 | 정렬 | 비교하지 않는 정렬. 값 범위가 곧 계약의 경계값이 되는 경우 |
| 너비 우선 탐색 | 그래프 | 같은 그래프를 훑는 두 갈래 중 하나. 방문 순서가 출력의 일부 |
| 깊이 우선 탐색 | 그래프 | 나머지 한 갈래. 같은 입력에 다른 순서가 나오는 이유 |
| A* | 그래프 | 휴리스틱으로 유망한 쪽부터. 동률 f 점수를 무엇으로 가르는가 |
| KMP | 문자열 | 패턴 하나 찾기 |
| 아호 코라식 | 문자열 | 패턴 여럿을 한 번에. 겹치는 일치를 어떻게 보고하는가 |

**8종이 서로 짝이 되게 놓여 있습니다.** 알고리즘 하나를 혼자 보는 것보다 "이건 되는데 저건
왜 안 되는가"를 나란히 놓고 보는 편이 계약의 성격 차이를 드러냅니다. 정렬 세 종은 비교 기반
둘과 비비교 하나, 그래프 세 종은 무정보 탐색과 휴리스틱 탐색, 문자열 두 종은 단일 패턴과
다중 패턴으로 갈립니다.

정렬 세 종은 특히 나란히 볼 값이 있습니다. 셋 다 출력은 `values` 하나(입력과 같은 값을
담은 오름차순 배열)로 같지만, 거기까지 가는 방법이 다릅니다. 버블 정렬은 인접한 값을
반복해 맞바꾸고, 퀵 정렬은 피벗으로 갈라 재귀로 내려가고, 계수 정렬은 값을 비교하지 않고
셉니다. 계약이 입력에 거는 조건도 종마다 다릅니다. 계수 정렬만 값의 폭에 상한이 있고, 그
상한을 넘으면 `INPUT_TOO_LARGE`로 거절합니다. **출력 모양이 같다고 계약까지 같지는 않다**는
것, 그리고 **계약은 무엇을 보장하는지만 말하고 어떻게 하는지는 말하지 않는다**는 것이 여기서
드러납니다.

각 알고리즘은 **C# · Java · JavaScript** 세 언어 구현을 함께 싣습니다. 세 언어는 정적 강타입 ·
JVM · 동적이라는 축이 서로 달라서, 같은 계약이 언어에 따라 어떻게 다른 모양으로 나오는지가
한 화면에서 비교됩니다.

싣고 있는 **공식 테스트 케이스는 70건**이고, 세 언어가 같은 케이스를 공유하므로 검사는
**210건**입니다. 실패 0건 · 건너뜀 0건입니다.

## 3. 읽는 순서

화면은 **목록 · 커버리지 · 상세** 셋입니다. 아래 순서를 따라가면 셋을 한 번씩 지납니다.

### ① 목록에서 고릅니다

카드형과 리스트형을 전환할 수 있고, 분류 필터와 검색이 있습니다. 검색은 한국어 이름
("너비 우선 탐색")과 영문 약어("bfs")로 둘 다 걸립니다.

### ② 상세에서 계약과 테스트를 먼저 봅니다

상세 화면은 설명에서 끝나지 않습니다. **그 알고리즘이 무엇을 보장하는지(계약), 무엇으로
증명됐는지(실제 테스트 케이스)**가 함께 나옵니다.

| 영역 | 내용 |
|---|---|
| 설명 | 요약 · 언제 쓰나 · 언제 피하나 · 트레이드오프 · 함정 |
| 사용 시나리오 | 상황 · 왜 이 알고리즘인가 · 적용 · 전환점 |
| 계약 | 입력 · 출력 · 오류 코드 · 입력 변이 규칙 |
| 복잡도·전제조건 | 시간·공간, 그리고 동률 처리처럼 결과를 가르는 규칙 |
| 테스트 케이스 | **실제로 돌린 벡터의 입력과 기대 출력 JSON** |

읽는 순서를 굳이 권한다면 **계약 → 테스트 케이스 → 설명** 순입니다. 설명은 사람이 쓴
글이지만 계약과 테스트 케이스는 검증이 실제로 확인한 것이라, 둘이 어긋나면 계약 쪽이
사실입니다.

### ③ 코드 비교에서 언어별 구현을 봅니다

언어별 **원본 소스 전문**과 진입점, 검증 통과 요약이 나란히 놓입니다. 소스는 복사해 갈 수
있습니다. 한 알고리즘이 한 파일에 담겨 있어서 **그 파일만 가져가도 다른 파일 없이
동작**합니다.

### ④ JavaScript는 그 자리에서 돌려 봅니다

JavaScript 카드에는 실행기가 붙어 있습니다. 케이스를 고르고 실행을 누르면 **위에 떠 있는 그
소스**가 브라우저에서 돌고, 결과가 케이스의 기대값과 대조됩니다. 자세한 동작은 4절에 있습니다.

### ⑤ 커버리지에서 전체를 한 표로 봅니다

종별 **벡터 수 · 케이스 수 · 언어 상태**가 한 표에 모입니다. 상세를 여덟 번 열지 않고도 어느
종에 케이스가 몰려 있는지, 어느 종이 몇 건으로 잠겨 있는지가 한눈에 들어옵니다. 이 스냅샷은
세 언어만 실었으므로 나머지 언어 칸은 상태 기호로만 남고, 기호의 뜻은 표 아래 범례에
있습니다.

## 4. 브라우저에서 돌려 보기

이 사이트에서 가장 눈에 띄는 기능입니다. **읽고 있는 그 구현이 정말 계약대로 도는지를 화면을
떠나지 않고 확인**할 수 있습니다.

### 무엇을 무엇으로 돌리는가

| | |
|---|---|
| 돌리는 것 | 화면이 **무결성 검사를 통과해 받아 둔 소스 바이트 그 자체**. 실행하려고 따로 받아오지 않습니다 |
| 넣는 것 | 함께 실린 **공식 벡터의 케이스**. 파이프라인이 열 개 언어에 쓰는 바로 그 입력 |
| 대조하는 것 | 그 케이스가 선언한 **기대값 또는 기대 오류 코드** |

눈에 보이는 코드와 실제로 도는 코드를 다른 경로로 두지 않은 것이 요점입니다. 둘이 갈리면
"돌려 봤다"가 아무것도 증명하지 않습니다.

### 격리와 시간 제한

- 실행은 **브라우저에 내장된 별도 스레드(Web Worker 표준 API) 안에서만** 일어납니다. 워커
  스크립트는 파일이 아니라 받아 둔 소스 바이트로 그 자리에서 만들어 띄우므로, 실행하려고
  밖으로 나가는 요청이 없습니다.
- 화면을 그리는 스레드와 분리돼 있어 DOM에 손댈 수 없고, 무한 루프가 돌아도 화면이 멈추지
  않습니다.
- **2초를 넘기면 밖에서 워커를 종료**합니다. 협조를 구하는 신호가 아니라 강제 종료라
  `while (true)`도 실제로 끊깁니다.
- 통과 · 실패 · 시간 초과 · 실행 오류 넷을 모두 **화면에 값으로** 표시합니다. 콘솔을 열어야
  알 수 있는 결과는 없습니다.

### 입력을 고쳐서 돌려도 됩니다

입력 JSON은 편집할 수 있고, 케이스 원본으로 되돌리는 버튼이 함께 있습니다. 값을 바꿔 돌리면
**계약이 무엇을 거절하는지 직접 밟아 볼 수 있습니다**. 32비트 범위를 넘겨 보거나, 빈 패턴을
넣어 보거나, 없는 정점을 출발점으로 줘 보는 식입니다. 고쳐 돌린 결과에는 "기대값은 원래
케이스의 것"이라는 표시가 붙습니다.

### 판정을 느슨하게 두지 않았습니다

출력을 기대하는 케이스는 **값이 정확히 같아야** 통과입니다(키 순서만 무시합니다). 오류를
기대하는 케이스는 **계약이 선언한 오류 코드까지 같아야** 통과입니다. 아무 예외나 났다고
통과시키면 오류 계약을 검사하지 않는 것과 같습니다.

준비되지 못하는 경우도 있습니다. 소스나 벡터를 무결성 검사대로 읽지 못하면 실행을 막고, **왜
돌릴 수 없는지를 그 자리에 적습니다.** 눌러도 아무 일이 없는 버튼을 남겨 두지 않습니다.
코드 표시와 같은 검사를 통과해야 실행도 됩니다.

브라우저가 그대로 돌릴 수 있는 언어가 JavaScript뿐이라 실행기는 그 카드에만 붙습니다. 나머지
두 언어는 파이프라인이 남긴 검증 결과 요약으로 확인합니다.

## 5. 사용 시나리오를 다시 쓴 이유

상세의 **사용 시나리오**는 여덟 종 가운데 여섯 종을 공개 스냅샷에 맞춰 다시 썼습니다. 본체의
시나리오는 이미 그 알고리즘을 쓰기로 정한 시스템의 내부 사정에서 출발합니다. 어느 배치가 몇
분마다 돌고, 어느 파티션이 어떻게 합쳐지는지 같은 이야기입니다. 정확하지만, **처음 보는
사람에게는 그 상황 자체가 설명을 필요로 합니다.**

그래서 공개용 시나리오는 **일상에서 이미 겪어 본 장면**에서 시작하도록 고쳐 썼습니다. 원고
편집기에서 모두 찾기를 누르는 순간, 배달 시간이 몇 분 빗나갔는지 모아 보는 화면 같은 것들
입니다. 네 부분의 역할도 그에 맞춰 고정했습니다.

| 부분 | 하는 일 |
|---|---|
| 상황 | 겪어 본 장면 하나. 여기서 **무엇이 까다로운지**까지 같이 짚습니다 |
| 왜 이 알고리즘인가 | 그 까다로움을 이 알고리즘이 **어떤 방식으로** 없애는지, 그 대가로 무엇을 치르는지 |
| 적용 | 계약의 입력 · 출력 · 오류를 그 장면의 말로 옮긴 것 |
| 전환점 | **이 알고리즘을 그만 써야 하는 지점**과 그때 넘어갈 곳 |

마지막 칸이 특히 값을 합니다. 알고리즘 설명은 보통 "언제 쓰는가"에서 끝나는데, 실제로
필요한 판단은 **"언제부터는 이걸 쓰면 안 되는가"**입니다. 그 자리를 비워 두면 읽은 사람이
경계를 스스로 상상하게 되고, 상상한 경계는 대개 실제보다 넓습니다.

남은 두 종은 본체의 글을 그대로 두었습니다. 덕분에 **두 방식을 나란히 비교해 볼 수
있습니다**. 같은 알고리즘 설명이라도 어디서 출발하느냐에 따라 읽는 데 필요한 준비물이
얼마나 달라지는지가 사이트 안에서 그대로 드러납니다.

이 다시 쓰기는 **이름만 알던 알고리즘을 제대로 알아보자**는 출발점과 이어집니다
([프로젝트 소개](../README.md#1-가볍게-시작했습니다)). 계약을 다 적고 나서도 "이걸 언제
쓰는가"는 여전히 안 적혀 있었고, 그 자리를 채우려면 알고리즘을 한 번 더 이해해야 했습니다.
그 과정은 [실험 노트](experiment-notes.md#3-계약을-적으며-배운-것)에 적었습니다.

## 6. 화면에서 신경 쓴 것

- **다크 모드는 토글, 라이트가 기본**입니다. 다크일 때만 속성을 남기고 라이트는 속성 없음이
  기본 상태입니다. 기본값을 속성으로 표현하지 않으면 초기 렌더 깜빡임을 막기 쉽습니다.
- 네비게이션은 탭이 아니라 **실제 링크**입니다. 각 항목이 진짜 주소를 가지므로 뒤로 가기와
  새 탭 열기가 자연스럽게 동작합니다. 사이드바는 좁은 화면에서만 드로어로 접힙니다.
- **이름 표기 토글(한국어/English)**이 상단에 있습니다. 이름만 영문이 되고 주변 버튼·빈 상태
  문구가 한국어로 남으면 한 화면에서 표기가 갈리므로, UI 문자열 전부를 같은 토글이 함께
  지배하게 했습니다.
- 접근성은 텍스트 대비뿐 아니라 **비텍스트 대비(WCAG 1.4.11)**까지 봤습니다. 컨트롤·입력
  테두리는 안쪽 면과 바깥 패널 면 **양쪽에 대해 3:1**을 넘겨야 해서, 순수 장식선과 의미 있는
  경계선을 다른 토큰으로 분리했습니다. 장식선까지 3:1로 올리면 화면이 과하게 시끄러워집니다.
- 상세를 열면 키보드 초점이 상세 제목으로 이동하고, `prefers-reduced-motion`을 존중합니다.
- 클립보드 API가 없는 환경에서는 **복사 UI를 만들지 않습니다**. 눌러도 안 되는 버튼을
  보여 주는 대신 없앱니다.

### 한국어 표기와 검색

카탈로그의 ID와 이름은 영문입니다. 그대로 두면 **"버블"로는 `bubble-sort`를 찾을 수 없고**,
화면 제목도 영문 하나뿐입니다. 이 스냅샷에 버블 정렬이 실려 있으니 목록 검색창에서 그대로 해
볼 수 있습니다. 그래서 성격이 다른 표 세 개를 뒀습니다.

| 표 | 성격 |
|---|---|
| 한국어 표시명 | 화면에 실제로 찍히는 **대표 표기 하나** |
| 한국어 검색 별칭 | 같은 대상을 여러 갈래로 걸리게 하는 **별칭 여럿** |
| 영문 약어 | **부분 표**: `bfs`, `lcs`처럼 교과서·현업에서 그대로 쓰이는 두문자어만 |

표시명과 검색 별칭을 합치지 않은 이유가 있습니다. 하나로 합치면 "첫 별칭이 대표 표기"라는
암묵 규칙이 생기고, 검색을 잘 걸리게 하려고 별칭을 추가하다가 화면 제목이 따라 바뀝니다.
대신 **표시명은 전부 검색으로도 걸려야 한다**는 제약을 테스트가 전수로 확인합니다.

표기 원칙은 직역보다 통용성이 먼저입니다. 정착된 한국어 용어가 있으면 그것을 쓰고("이진
탐색", "위상 정렬"), 없으면 외래어 표기를 씁니다("랑데부 해싱"). 사람 이름에서 온 알고리즘은
제목 자리에서 사람으로 읽히지 않도록 하는 일을 덧붙입니다("프림 최소 신장 트리").

약어 표는 반대로 **넣지 않는 기준**이 더 중요했습니다. `segtree`·`toposort`처럼 임의로 줄인
표기는 만들지 않습니다. 그런 검색어는 풀네임 부분 일치로 이미 걸리고, 임의 약어를 늘리면
표가 개인 취향의 사전이 됩니다.

## 7. 화면 문체가 다른 이유

문서는 `-습니다`체인데 사이트에 실린 알고리즘 설명과 사용 시나리오는 `-어요`체입니다.
의도한 구분입니다. 설계를 설명하는 글과, 알고리즘을 처음 보는 사람에게 건네는 콘텐츠는
읽는 상황이 다릅니다.
